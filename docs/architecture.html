01Le modele mental

Quatre plans, quatre questions distinctes. C'est la decoupe qui tient tout le reste : chaque module appartient a un seul plan, et aucun plan ne depend de l'etat d'un autre pour fonctionner.

Plan 1 · Realite

Ce qui existe

L'API OVH dit quelles machines sont facturees. L'API Proxmox dit ce qui tourne dessus. Source de verite materielle, jamais saisie a la main.

Plan 2 · Accessibilite

Ce qui est joignable

The Bastion dit qui a le droit d'atteindre quoi. Comparer les deux plans revele les trous : machine connue mais inaccessible, acces declare vers une machine disparue.

Plan 3 · Signification

Ce que ca veut dire

Les tags portent l'intention humaine : production, a decommissionner, hors perimetre. L'API ne les devine pas, la base les conserve.

Plan 4 · Action

Ce qu'on en fait

Le client transforme l'inventaire en cibles Ansible. Un jeton a usage unique relie l'intention de l'operateur a l'execution.

Pourquoi cette separation compte

La collecte tourne sans le web, le web sert sans le client, le client fonctionne sur un cache. Une panne de MariaDB n'empeche pas une collecte de reussir en memoire ; une panne d'Authentik n'empeche pas un playbook deja prepare de tourner. Chaque lien est volontairement faible.

02Flux principal

Le chemin d'une donnee, de l'appel HTTP jusqu'au playbook. Les fleches teal portent les donnees d'inventaire ; les grises, les secrets et les appels de controle.

Les deux couches de secrets

secrets_infra.py n'a aucune dependance et lit les deux secrets d'amorcage — le mot de passe de la base et la clef maitresse. secret_store.py s'appuie dessus pour dechiffrer tout le reste. L'ordre compte : le premier doit fonctionner quand la base est en panne, ce qui est precisement le moment ou on en a besoin.

04Deduplication des clusters PVE

Le mecanisme le plus subtil de la collecte, et celui qui n'a jamais tourne sur le vrai parc. Interroger les 30 dedies naivement reviendrait a collecter chaque cluster autant de fois qu'il a de noeuds.

Non eprouve

Le parc genere par generer_demo.py produit des donnees deja dedupliquees : il fabrique directement un representant par cluster. Le chemin de regroupement n'a donc jamais tourne sur des sondes reelles multiples. C'est le premier test a faire en preprod, avec au moins un cluster a trois noeuds et un noeud volontairement eteint.

05Base de donnees

Snapshots complets, pas de deltas : chaque collecte reecrit l'etat entier et conserve l'historique. La lecture courante passe par des vues, jamais par une requete qui devrait deviner la derniere execution.

Tables

TableClefContenuColonnes notables
collect_runid Une ligne par collecte. Pivot de tout l'historique. status (running / ok / partial / error) · nb_unreachable
server_snapshotrun_id + ovh_name Les dedies vus cote OVH. offer · datacenter · expiration · cpu_* · ram_mb
node_snapshotrun_id + host Les hyperviseurs PVE, un par machine physique. cluster_name · reachable · error · pve_version · kernel
guest_snapshotrun_id + vmid VM et conteneurs. via_host · guest_type · status · tags · disk_gb
client_tokenempreinte Jetons a usage unique. Le jeton en clair n'est jamais stocke. empreinte CHAR(64) · expire_le · consomme_le · consomme_de

Vues

v_last_run isole la derniere execution reussie ; v_current_servers, v_current_nodes et v_current_guests s'y adossent pour ne rendre que l'etat courant ; v_current_inventory aplatit l'ensemble en une ligne par hote. Toute requete d'exploitation passe par la : si un jour la strategie de snapshot change, le code appelant ne bouge pas.

Deux pieges deja rencontres

via_host dans guest_snapshot enregistre par quel noeud l'invite a ete vu, ce qui n'est pas forcement le noeud qui l'heberge (pve_node). Sans cette distinction, un invite migre semble changer de machine a chaque collecte.

Les colonnes DECIMAL remontent en Decimal Python, que json.dumps refuse. C'est le role de _json_ok() dans inventory_db.py.

Nommage des hotes invites

Le vmid en suffixe garantit l'unicite : deux clusters peuvent heberger une web01, et un nom seul creerait une collision silencieuse dans l'inventaire.

Le piege du format

Le JSON produit par --list est le format d'un inventaire dynamique : ansible-playbook -i fichier.json le refuse. Le client le reecrit donc en format natif avant de le passer a Ansible :

{"all": {"hosts": {…}, "children": {…}}}

07Flux du jeton a usage unique

Le jeton relie une identite authentifiee par Authentik a une execution Ansible sur le poste de l'operateur, sans que le poste ait a detenir de secret durable.

Routes du service

RouteMethodeAuthentificationReponse
/api/tokenPOSTEn-tete X-Remote-User pose par ApacheJeton en clair, une seule fois
/api/inventaireGETAuthorization: Bearer, consomme le jetonInventaire Ansible complet
/api/santeGETAucuneAge du snapshot, compteurs ok degrade
/GETAucuneLe schema, si --page est fourni
Pourquoi l'identite vient d'un en-tete

Le service n'ecoute que sur 127.0.0.1. Il ne peut donc recevoir que du trafic deja passe par Apache, qui a valide la session OIDC et pose X-Remote-User. Le jour ou le service serait expose directement, cet en-tete devient falsifiable par n'importe qui : l'ecoute locale est le controle d'acces, pas une commodite.

08Bastion et acces

The Bastion est l'autorite d'acces : comptes nominatifs, droits par groupe, traces centralisees. Le comparatif ne modifie rien, il expose les ecarts entre ce qui existe et ce qui est joignable.

Les trois etats

EtatSignificationAction attendue
declare La machine est dans l'inventaire et un acces la couvre. Rien.
manquant Machine inventoriee, dans le perimetre, mais aucun acces ne la couvre. groupAddServer — commande generee par --bastion-commands, jamais executee automatiquement.
hors perimetre Exclusion deliberee : os: win*, tag no-bastion, ou hote liste. Rien, mais l'exclusion reste visible dans le rapport.

Aujourd'hui le hors-perimetre represente moins de 10 % du parc, essentiellement les Windows. L'interet de l'etat explicite est qu'il ne se confond pas avec un oubli : une machine absente du bastion est soit un trou, soit une decision, et le rapport les distingue.

Couverture d'un acces

La fonction couvre() accepte une adresse seule ou un CIDR, et des jokers sur l'utilisateur et le port. Un acces 10.0.0.0/24 · root · 22 couvre bien 10.0.0.42 en root sur 22, mais pas le meme hote en ansible : la distinction compte, puisque les noeuds se joignent en root et les invites en ansible.

Non eprouve

La structure reelle de selfListAccesses --json-greppable n'a pas ete observee sur une instance vivante. acces_depuis_charge() visite l'arbre JSON de facon defensive, mais la premiere execution reelle demandera probablement un ajustement. Capture la sortie brute dans un fichier et passe-la a --acces avant de brancher --commande.

09Secrets

Trois sources, par ordre de preference. Le principe : aucun secret en clair sur le disque, et aucun secret dans l'environnement du processus.

References dans la configuration

# infra.yml — aucune valeur en clair
pve:
  default_token: "env:PVE_TOKEN"     # systemd-creds d'abord, puis la variable
db:
  password: "env:INVENTORY_DB_PASSWORD"

# resoudre() comprend aussi la forme explicite :
  token: "cred:pve_token"          # systemd-creds uniquement

env:NOM cherche d'abord un secret systemd nomme nom, puis NOM, puis la variable d'environnement. C'est ce qui permet de basculer une configuration existante sous systemd-creds sans la reecrire.

Mise en place

deploy/chiffrer-secrets.sh lit /etc/inventaire-infra.env, chiffre chaque variable separement, et deplace le fichier en clair vers .avant-chiffrement plutot que de le supprimer — si une unite n'etait pas encore convertie, le service ne demarrerait plus. Verifie que les services tournent, puis shred -u.

Decision retenue — chiffrement d'enveloppe

Les secrets sont stockes chiffres en base ; la cle maitresse qui les dechiffre reste protegee par systemd-creds. Deux elements separes qui doivent se rencontrer : un vidage de la base ne donne rien, et un disque recupere sans le TPM ne donne rien non plus.

Trois conditions non negociables

La cle maitresse uniquement dans la collecte. Le service web touche la meme base : s'il portait la cle, une faille dans le service expose derriere Apache donnerait tous les jetons. LoadCredentialEncrypted=master_key dans inventaire-collecte.service, jamais dans inventaire-web.service.

Un compte MariaDB distinct pour le web, sans aucun droit sur secret_store. Les valeurs y sont chiffrees, donc illisibles sans la cle, mais il n'y a aucune raison de les lui exposer.

L'outil de rotation ecrit le premier jour. Changer la cle maitresse impose de dechiffrer puis rechiffrer chaque ligne. La colonne cle_version permet de le faire progressivement, secret par secret, au lieu d'un basculement atomique impossible a reprendre en cas d'echec.

La table

CREATE TABLE IF NOT EXISTS secret_store (
  nom         VARCHAR(64)    NOT NULL,     -- pve_token, ovh_application_key…
  version     INT            NOT NULL,     -- incremente a chaque rotation
  nonce       VARBINARY(12)  NOT NULL,     -- unique par chiffrement, jamais reutilise
  chiffre     VARBINARY(512) NOT NULL,     -- valeur + tag d'authentification
  cle_version INT            NOT NULL,     -- quelle cle maitresse a chiffre
  cree_le     DATETIME       NOT NULL,
  cree_par    VARCHAR(190)   NOT NULL,     -- qui l'a pose
  actif       TINYINT(1)     NOT NULL DEFAULT 1,
  PRIMARY KEY (nom, version)
);

Versionner plutot qu'ecraser : l'ancienne valeur reste disponible le temps de verifier que la nouvelle fonctionne. La lecture prend la version active la plus haute.

Gestion interactive — inventory --ovh

Renouveler un jeton ne doit demander ni editeur, ni fichier temporaire, ni variable d'environnement qui resterait dans l'historique du shell. La saisie se fait sans echo, le jeton est teste avant d'etre ecrit, et l'ancienne version reste en place si le test echoue.

$ inventory --ovh

  Cle actuelle : ovh_application_key v3, posee le 2026-08-14 par evan
  Laisser vide pour conserver la valeur en place.

  Application key    : [saisie masquee]
  Application secret : [saisie masquee]
  Consumer key       : [saisie masquee]

  Test de la signature  GET /me  . . . . . . . . . [OK]  compte ab12345-ovh
  Test du droit de lecture  GET /dedicated/server  [OK]  31 serveurs
  Test du droit  GET /dedicated/server/*/serviceInfos  [OK]

  Enregistre : ovh_application_key v4, ovh_application_secret v4, ovh_consumer_key v4
  Version precedente conservee (v3), inactive.

Le cas d'echec compte autant que le cas nominal :

  Test de la signature  GET /me  . . . . . . . . . [KO]
  INVALID_SIGNATURE — la cle ou le secret ne correspondent pas.

  Rien n'a ete ecrit. La cle v3 reste active.

Pseudo-code

commande --ovh:
    etat = lire_version_active("ovh_application_key")
    afficher etat                       # version, date, auteur

    valeurs = {}
    pour chaque champ dans (app_key, app_secret, consumer_key):
        saisie = lire_sans_echo(invite)          # getpass
        si saisie est vide:
            si une valeur existe deja -> reprendre l'ancienne
            sinon -> erreur, champ obligatoire
        sinon:
            valeurs[champ] = saisie.strip()      # un espace colle tue la signature

    # tester AVANT d'ecrire : un jeton KO ne remplace jamais un jeton OK
    resultat = tester(valeurs)
    si resultat.echec:
        afficher resultat.motif
        sortir 1                        # rien n'a ete ecrit

    cle, cle_version = charger_cle_maitresse()   # $CREDENTIALS_DIRECTORY/master_key
    dans une transaction:
        pour chaque champ, valeur dans valeurs:
            nonce  = octets_aleatoires(12)
            chiffre = aead_chiffrer(cle, nonce, valeur, aad=champ)
            v = version_active(champ) + 1
            inserer(champ, v, nonce, chiffre, cle_version, maintenant, utilisateur)
            desactiver(champ, v - 1)             # conservee, plus active

    afficher le resume


tester(valeurs):
    client = OvhClient(endpoint, *valeurs)
    # /me valide la signature : si elle passe, les cles sont bonnes
    si echec sur /me                     -> KO, distinguer signature / reseau
    # les chemins metier valident les droits de la cle consommateur
    si echec sur /dedicated/server       -> KO, droit manquant, et lequel
    rendre OK + nb de serveurs vus
Pourquoi deux tests distincts

C'est la distinction que ovh_inventory.py fait deja, et elle vaut d'etre rendue visible ici. Une signature invalide est fatale — rien ne marchera. Un droit manquant laisse la collecte fonctionner avec des champs vides. Afficher les deux separement evite de passer une heure a regenerer des cles correctes parce que la vraie cause etait un droit absent sur la cle consommateur.

Les autres sous-commandes

Meme forme pour --pve <hote>, qui teste /version puis /cluster/status sur le noeud concerne — avec l'epinglage du certificat, comme la collecte, puisqu'un jeton valide sans epinglage et utilise ensuite avec epinglage ne prouve rien. Aucune sous-commande n'accepte de valeur en argument : un ps l'exposerait a tous les utilisateurs de la machine.

Deux sous-commandes qui ne suivent pas la regle

--db n'ecrit rien en base. Le mot de passe de la base ne peut pas y vivre, donc la commande teste puis affiche les trois etapes a executer. Son test echoue forcement au premier passage, avant que le ALTER USER soit joue : c'est pourquoi elle rend 0 dans les deux cas, et dit laquelle des deux situations on a.

--init-key et --rotate-key (sans --appliquer) n'ouvrent pas la base du tout. Tirer une clef ne doit pas dependre d'un service qui n'y a aucun role, et ces commandes servent justement quand rien n'est encore en place.

Rotation de la clef maitresse

En trois temps, parce que les deux clefs doivent etre lisibles pendant le rechiffrement.

# 1. sceller la clef a venir, sans toucher l'actuelle
inventory --rotate-key | sudo systemd-creds encrypt \
    --name=master_key_nouvelle - \
    /etc/inventaire-infra/creds/master_key_nouvelle.cred

# 2. charger les DEUX clefs dans l'unite, puis rechiffrer
inventory --rotate-key --appliquer

  ovh_application_key ......... [OK]  v5 en clef v2
  pve_token_ns1234_ip_1_2_3_eu  [OK]  v2 en clef v2
  31 rechiffre(s), 0 echec(s).

# 3. permuter les fichiers .cred, retirer master_key_nouvelle

Le rechiffrement se fait secret par secret, pas en une transaction : trente secrets ne se reprennent pas si la machine tombe au milieu. La colonne cle_version dit ou on s'est arrete, une seconde execution reprend le reste, et --list signale de lui-meme une rotation inachevee quand deux versions de clef coexistent.

Deux pieges de durcissement

IPAddressDeny=any aurait bloque l'acces a une MariaDB distante. La directive est commentee dans l'unite, avec l'explication : la reactiver suppose une base locale ou une regle d'autorisation explicite.

Les scripts shell doivent arriver en LF. Sous Windows, Path.write_text reintroduit des CRLF et rend le script illisible par bash. D'ou l'ecriture binaire cote Python et .gitattributes cote depot.

Cote poste operateur

# recuperer l'inventaire avec un jeton pris sur la page web
infra update --token <jeton> --url https://inventaire.exemple.net

# explorer sans rien executer
infra list web           # filtre sur le nom ou les tags
infra list --groupes

# verifier puis agir
infra simulate playbook.yml --limit cluster_prod1
infra run      playbook.yml --limit cluster_prod1

Le cache local a une duree de vie de quelques heures. run demande confirmation sauf avec --oui, et simulate est un --check : les deux partagent exactement la meme construction de cibles, pour qu'une simulation valide corresponde a l'execution.

11Configuration

Un seul fichier, infra.yml, lu par tous les modules via --config ou $INFRA_CONFIG. Aucune valeur sensible n'y figure en clair.

ovh:
  endpoint: ovh-eu              # api.ovh.com/1.0 — voir la note ci-dessous
  config: ~/.ovh.conf

pve:
  port: 8006
  pin_certs: true               # epinglage plutot que verify=False
  pin_dir: pinned
  default_token: "env:PVE_TOKEN"
  tokens: {}                    # par hote, si un cluster a son propre jeton
  skip: []
  detail: true                  # interroge l'agent QEMU pour les IP et l'OS

cache:
  path: .infra_cache.json
  ttl: 900

ansible:
  comptes:
    node: root                  # les hyperviseurs
    vm: ansible                 # les invites
  bastion:
    host: bastion.exemple.net
    groupe: infra-prod
    actif: false
    hors_perimetre:
      os: ["win*"]
      tags: ["no-bastion"]

db:
  host: 127.0.0.1
  user: inventory
  password: "env:INVENTORY_DB_PASSWORD"
  auto_schema: true
  keep_runs: 200                # purge au-dela
L'endpoint OVH

eu.api.ovh.com sert un certificat auto-signe, alors que le DNS est coherent et que les autres hotes repondent correctement. L'endpoint retenu est api.ovh.com/1.0 ; l'ancien reste disponible sous la clef ovh-eu-alt.

Identifiants invalides contre droits manquants

Le client OVH distingue les deux. Un INVALID_KEY ou INVALID_SIGNATURE est fatal : rien ne marchera, autant s'arreter. Un simple refus sur un chemin signifie que la clef consommateur manque un droit : le module continue et le champ reste vide. Sans cette distinction, une clef revoquee produisait un inventaire vide mis en cache, qui masquait l'erreur pendant 15 minutes.

12Ce qui reste

L'etat honnete du projet : ce qui a tourne pour de vrai, et ce qui n'a jamais rencontre la realite.

Eprouve

  • Collecte reelle de bout en bout : 1 dedie, 3 VM, snapshot en base.
  • Parc genere a l'echelle : 30 dedies, 308 invites, 338 hotes, 66 groupes, 378 cartes rendues en 16 ms.
  • Flux du jeton complet : emission depuis la page, consommation par le client, refus au rejeu.
  • simulate et run valides avec Ansible 2.14.

Non eprouve

  • Deduplication de cluster sur un vrai parc — les donnees generees sont deja dedupliquees.
  • Structure de selfListAccesses sur une instance vivante du bastion.
  • Vhost Apache avec un vrai Authentik : le parcours OIDC complet n'a pas ete suivi.
  • Installation reelle : seule une simulation a tourne.

Eprouve sans base

Ce qui se teste sur un poste nu l'a ete : les 16 tests du chiffrement, la generation de clef, le refus de saisie non interactive, les messages d'erreur, et --list sur une fausse connexion — y compris sa detection d'une rotation inachevee.

Ecrit, jamais execute

Tout ce qui ecrit. Ces quatre blocs se relisent mais n'ont jamais rencontre une vraie base : c'est le gros du risque restant.

  • La couche SQL de secret_store — lire, ecrire et lister.
  • Le DDL et les GRANT — dont les deux requetes de verification en fin de setup_db.sql, qui doivent ne rien renvoyer.
  • La resolution db: — testee sur le chemin d'echec, jamais sur le chemin nominal.
  • Les sous-commandes qui ecrivent — --ovh, --pve, --rotate-key --appliquer.

A ecrire

  • MFA sur le parcours web : prevu, pas commence.

Sur la VM

Le detail est dans docs/deploiement.md, que l'installeur copie sur la machine : dix etapes dans l'ordre ou elles doivent se faire, chacune avec sa verification, et une section de retour arriere par gravite croissante. Les grandes lignes :

  1. La base et les deux comptes, puis les deux requetes de verification — une ligne renvoyee signifie que la separation ne tient pas.
  2. Une collecte sur un seul hote, secrets encore en clair. C'est la qu'on eprouve la deduplication de cluster : un cluster a trois noeuds, dont un volontairement eteint.
  3. Sceller la clef maitresse, dans l'unite de collecte uniquement.
